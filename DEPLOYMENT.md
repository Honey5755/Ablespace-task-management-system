# Deployment

Three free-tier services: **Neon** (PostgreSQL), **Render** (NestJS API),
**Vercel** (Next.js web). Roughly 20 minutes end to end.

The order matters — each step needs a URL from the one before it.

---

## 1 · Database — Neon

1. Sign up at [neon.tech](https://neon.tech) and create a project
2. Copy the **pooled** connection string from the dashboard
3. Make sure it ends with `?sslmode=require`

```
postgresql://user:pass@ep-xxx-pooler.region.aws.neon.tech/neondb?sslmode=require
```

Use the **pooled** endpoint (it has `-pooler` in the host). Render's free tier
opens more connections than a direct endpoint allows.

## 2 · API — Render

1. [dashboard.render.com](https://dashboard.render.com) → **New** → **Blueprint**
2. Connect the GitHub repo — Render reads [`render.yaml`](render.yaml)
3. Set the two secrets it prompts for:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | the Neon string from step 1 |
| `CORS_ORIGIN` | leave as `http://localhost:3000` for now; corrected in step 4 |

`JWT_SECRET` is generated by Render automatically — don't set it by hand.

The build runs `npm run db:deploy`, which applies the committed migrations in
`apps/api/prisma/migrations/`. No manual SQL.

Once live, note the URL — e.g. `https://pyramid-api.onrender.com`.

Verify it before continuing:

```bash
curl -i https://pyramid-api.onrender.com/api/auth/me      # expect 401
curl -X POST https://pyramid-api.onrender.com/api/auth/guest \
     -H 'Content-Type: application/json' -d '{}'          # expect a token
```

A `401` is the correct answer for the first one — it proves the route is
mounted and the guard is active.

## 3 · Web — Vercel

1. [vercel.com/new](https://vercel.com/new) → import the repo
2. **Root Directory:** `apps/web`
3. Framework preset: Next.js (auto-detected)
4. Environment variable:

| Variable | Value |
| --- | --- |
| `NEXT_PUBLIC_API_URL` | `https://pyramid-api.onrender.com/api` |

The `/api` suffix matters — the Nest app sets that global prefix.

Deploy, then note the URL, e.g. `https://pyramid-xxx.vercel.app`.

## 4 · Close the CORS loop

Back in Render → **Environment** → set:

```
CORS_ORIGIN = https://pyramid-xxx.vercel.app
```

Save and let it redeploy. Until this is done the browser blocks every API call
and the app looks broken while the API is perfectly healthy.

Multiple origins are comma-separated:
`https://pyramid.vercel.app,https://pyramid-git-main-you.vercel.app`

## 5 · Verify the deployment properly

Open the Vercel URL and check:

- [ ] Login screen renders with correct fonts and spacing
- [ ] **Continue as Guest** lands on the task list
- [ ] Create a task — it appears
- [ ] **Reload.** The task is still there ← *proves the database persists*
- [ ] Switch to dark, reload — still dark
- [ ] Open on a phone — sidebar collapses to a drawer
- [ ] Open in a private window — a fresh guest sees an **empty** board, not yours

The reload checks are the ones that matter. A deployment backed by a
non-persistent store passes every other check and still fails a reviewer.

---

## Notes

**Render free tier sleeps** after ~15 minutes idle and cold-starts in ~50
seconds. A reviewer hitting a sleeping instance may read it as broken. Options:

- Ping the health endpoint every 10 minutes with a free uptime monitor
  (UptimeRobot, cron-job.org)
- Or deploy the API to Railway / Fly.io instead, which don't sleep

The brief requires the deployment stay reachable for **45 days**, so this is
worth handling rather than hoping.

**Seeding production is optional.** Guests get an empty workspace by design.
To populate the demo account, run once against the production database:

```bash
DATABASE_URL="<neon-url>" npm run db:seed
```

**Rolling out schema changes:** commit a migration locally with
`npm run db:migrate -- --name what_changed`, push, and Render applies it via
`db:deploy` on the next build.
